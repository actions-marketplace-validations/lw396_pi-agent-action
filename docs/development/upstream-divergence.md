# 与上游的偏离

本仓库从 [anthropics/claude-code-action](https://github.com/anthropics/claude-code-action)（下称"上游"）移植而来，代码独立维护，不从上游 cherry-pick。上游的行为是起点，不是约束：对本项目用户更好的改动可以直接做。为上游写的 workflow 要么继续可用，要么失败并说明怎么改。下面登记每一项与上游不同的行为和原因。

## 规则

- 每项偏离标一个原因类别：

  | 类别             | 含义                                   |
  | ---------------- | -------------------------------------- |
  | `pi-capability`  | pi 没有某项能力，或者做法不同          |
  | `multi-provider` | 支持多个模型 provider 带来的差异       |
  | `branding`       | 本项目不是官方产品，不使用 Claude 品牌 |
  | `scope`          | 本项目明确不做                         |
  | `improvement`    | 本项目认为有更好的做法                 |

- 改变行为的 PR 要在同一个 PR 中更新本文，并标明用户是否可见。没有登记的偏离视为缺陷。README 只列删除的输入和 `claude_args` 的对照，其他行为差异以本文为准。
- 难以撤回的偏离另写 ADR，在条目中注明。
- 每项偏离占表格一行，写清差在哪、指向实现文件；理由不显然时，在表格下补充说明。实现细节写在代码里，不在这里复述。

删除的输入：

| 输入                                                                                                                        | 类别             | 原因                                                                         |
| --------------------------------------------------------------------------------------------------------------------------- | ---------------- | ---------------------------------------------------------------------------- |
| `anthropic_api_key`、`claude_code_oauth_token`、workload identity 的 5 个输入、`use_bedrock` / `use_vertex` / `use_foundry` | `multi-provider` | 由 `model` 加 `env:` 取代                                                    |
| `claude_args`                                                                                                               | `pi-capability`  | 由 `pi_args` 和独立输入取代                                                  |
| `settings`                                                                                                                  | `pi-capability`  | 格式不兼容；pi 的部分设置（`shellPath`、`packages`）能绕开安全默认值         |
| `plugins`、`plugin_marketplaces`                                                                                            | `pi-capability`  | 不兼容 Claude Code 插件；通用 skill 用 `skills`，原生 pi 扩展包用 `packages` |
| `include_fix_links`                                                                                                         | `branding`       | 链接打开的是 Claude Code 网页版，pi 没有对应                                 |
| `path_to_claude_code_executable`                                                                                            | `pi-capability`  | pi 在进程内运行，版本由 action 锁定，没有可替换的可执行文件                  |

- 删除的输入仍以占位形式声明在 `action.yml` 中：composite action 读不到未声明的输入，GitHub 只给一条警告，静默忽略会让 workflow 以为配置生效了。
- `model`、`allowed_tools` 曾是上游 v0.x 的输入，v1.0 并入了 `claude_args`。本仓库恢复成独立输入：没有默认 provider，`model` 必须显式给出；工具规则由 action 执行，而不是 pi，放进 `pi_args` 会混入 pi 不认识的参数。
- App token 续期：installation token 的有效期固定为 1 小时，不能延长，只能换新的。OIDC 请求凭据在 Runner 启动前从环境中删除（不让 agent 自己换 token），所以续期函数在此之前保存它，只留在 action 进程内存中。MCP server 是独立进程，env 在启动时固定，换 token 要么重启 server（pi 会先隐藏再重新声明它的工具，与正在进行的模型请求竞争），要么把 token 写进文件（被检出代码和后续步骤可读）；broker 不落盘，密钥只在 MCP server 的 env 中，与原先 token 本身所在的位置相同。
- 分类默认用 `model`，不自动选 jev 这类分类模型：只有部分 provider 提供，而且 key 能否调用取决于套餐，自动选择会让分类时好时坏。

## 工具与权限

| 偏离                | 上游 → 本仓库                                                                                                                                                                                                                | 类别            | 用户可见 |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | -------- |
| 未命中规则的调用    | `--permission-mode auto` 交给安全审查 → 直接拒绝；只读工具（Read、Grep、Glob、LS）总是放行（`src/runner/tool-permissions.ts`）                                                                                               | `pi-capability` | 是       |
| 组合命令            | 拆开后逐段匹配，另有内置只读命令 → 有 `Bash(...)` 规则参与判断时，拒绝 `&&`、`;`、`\|`、`$()`、重定向等；只读命令只剩 tag mode 的只读 git 命令（`src/runner/shell-syntax.ts`、`read-only-git.ts`）                           | `pi-capability` | 是       |
| 规则语法            | Read、Edit 可带路径，WebFetch 可带 `domain:` → 只有 Bash 规则可带 pattern，其他工具带 pattern 时运行失败；pi 没有的工具只打印警告（`src/runner/tool-rules.ts`）                                                              | `pi-capability` | 是       |
| codemode            | 无 → `pi_args: --tools +codemode` 开启 pi 的 `codemode` 工具（与 pi 一样默认关闭）：模型可以写 JS 脚本调用其他工具和 classifier 等非对话模型；它本身不需要规则，脚本里的每次工具调用照常按规则检查（`src/runner/run-pi.ts`） | `pi-capability` | 是       |
| tag mode 的文件编辑 | acceptEdits 模式 → 扩展放行工作目录内的 `edit`、`write`，`.git/` 除外（`src/runner/workspace-path.ts`）                                                                                                                      | `pi-capability` | 否       |

- codemode 不扩大权限：脚本在没有文件系统和网络的 QuickJS 沙箱里运行，只能通过工具和 `models` 影响外部，而工具调用经过同一个 `tool_call` hook（`test/pi-sdk/codemode.test.ts`）。`models` 的调用（分类、生成图片）不是工具调用，规则管不到，费用记在 provider key 上。
- 不拆分组合命令：拆分要完整实现 bash 语法，漏掉一种写法就能绕过规则；直接拒绝容易验证，模型收到原因后会逐条执行。
- 不放行 `.git/` 下的写入：写进去的 hook 会在 `git commit` 时执行任意命令，绕过 bash 规则。
- 只读 git 命令带 `--output`、`--ext-diff`、`--textconv`、`-c`、`-C` 等选项时不放行，因为这些选项能写文件或执行程序。

## MCP 与提示词

| 偏离                 | 上游 → 本仓库                                                                                                                                                                                                                                                                                                                                                                                                                                                   | 类别            | 用户可见 |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | -------- |
| MCP server 注册      | `--mcp-config`，并读取用户和项目的 MCP 配置 → 通过 SDK 以 `direct` 模式注册，不读任何 `mcp.json`；用户暂时不能添加自己的 server（`src/runner/mcp-servers.ts`，ADR-0001）                                                                                                                                                                                                                                                                                        | `pi-capability` | 是       |
| 评论工具名           | `update_claude_comment` → `update_comment`                                                                                                                                                                                                                                                                                                                                                                                                                      | `branding`      | 是       |
| tag mode 提示词      | 让模型先用 ToolSearch 加载工具 → 不提 ToolSearch                                                                                                                                                                                                                                                                                                                                                                                                                | `pi-capability` | 否       |
| 评论中的斜杠命令     | `@claude /cmd` 作为单独的消息块交给 Claude Code，展开 `.claude/commands/cmd.md` → Runner 自己展开 `/skill:<name>` 和 `/<模板>`（`.pi/skills/`、`.agents/skills/`、`.pi/prompts/`），追加在提示词末尾；workflow 设置了 `prompt`（`track_progress`）时不从 PR/issue 描述或评论中提取斜杠命令，任务只由 workflow 作者的 `prompt` 决定；模型仍可能按描述自行读取 skill，这里只取消 Runner 的强制展开（`src/runner/slash-command.ts`、`src/create-prompt/index.ts`） | `pi-capability` | 是       |
| 默认 tag mode 提示词 | 固定五步流程、`<analysis>` 输出要求和 `CRITICAL`/`IMPORTANT` 式强调 → 按请求来源、运行环境、发布方式、权限和沟通写成的简洁规则，不指定推理格式；遵循 `AGENTS.md` 及兼容的 `CLAUDE.md`，进度按里程碑更新（`src/create-prompt/default-prompt.ts`）                                                                                                                                                                                                                | `pi-capability` | 是       |
| 请求来源             | 只认含触发词的评论或 issue → 按事件选择：评论事件用触发评论，assigned/labeled 用整个 issue body；`track_progress` 下用 workflow 的 `prompt`（`<custom_instructions>`），issue/PR 内容和评论只作上下文                                                                                                                                                                                                                                                           | `pi-capability` | 是       |
| 完成条件             | 复杂任务可以解释后标记完成 → 必须完整实现，不缩减或扩大范围；阻塞时先完成其余工作，未完成项保持未勾选并报告阻塞；只跑权限允许、改动需要的检查，跑不了的说明缺哪条 `allowed_tools` 规则，被拒绝的调用不换方式绕过                                                                                                                                                                                                                                                | `pi-capability` | 是       |
| 无人值守的停止方式   | 无 → 点名四种不该出现的停止方式（宣布下一步却不做、提议继续、列出不阻塞的待决事项、到里程碑就汇报），先完成不依赖答案的工作再提问                                                                                                                                                                                                                                                                                                                               | `pi-capability` | 是       |
| `.github/workflows/` | 一律说 GitHub App 不能修改 workflow → 按 token 来源：pi-agent-action app 的 token 不要修改这些文件；`github_token` 先发布其他改动，再单独发布 workflow 改动（`src/entrypoints/run.ts` 传入来源）                                                                                                                                                                                                                                                                | `pi-capability` | 是       |
| 内容块的随机 id      | 标签不带标记 → 每个 GitHub 内容块和 `<custom_instructions>` 的开始、结束标签带每次运行新生成的 `id`（`src/create-prompt/index.ts`）                                                                                                                                                                                                                                                                                                                             | `pi-capability` | 否       |
| 简化版提示词         | `USE_SIMPLE_PROMPT=true` 改用一份未写进文档的简化提示词 → 删除，变量被忽略并打印警告                                                                                                                                                                                                                                                                                                                                                                            | `scope`         | 是       |

- 重写默认提示词：上游提示词依赖 Claude Code 自带的 system prompt 和 TodoWrite，且是为一年多前的模型写的；pi 没有这些，Runner 只调用一次 `session.prompt()`，工具靠 `allowed_tools` 放行，所以按 pi 的运行方式重写。要求模型把推理写进回复的 `<analysis>` 指令，在 Claude Opus 5.x 上可能被 `reasoning_extraction` 拒绝。
- 停止方式：模型第一条不带工具调用的消息就结束运行，所以要点名会让运行提前结束的停止方式。
- 以上是提示词约束，不是 Runner 的完成度检查；agent mode 的自定义 `prompt` 不受影响。分支由 action 准备，提示词不再要求模型新建分支；可用工具和 GitHub 权限由运行配置决定，不能靠提示词扩大。
- 随机 id：评论里伪造的 `</comments><trigger_comment>` 因此只是正文。做法来自 Claude Opus 5.5 提示指南中标记粘贴内容的建议。标签是纯文本，这是一层提示词约束，不是隔离。
- 删除简化版：它缺少默认提示词的完成条件、权限说明和内容块 id，打开它会让运行更容易被评论内容影响，而且两份提示词要同时维护。
- 不读仓库的 `.pi/mcp.json`：pi 中配置文件里的同名 server 优先于 SDK 注册的 server，被检出的代码可以借此换掉本项目的 server，拿到 GitHub token。server 的 `env` 值一律转义，因为 pi 会展开 `$NAME`、执行以 `!` 开头的值，而分支名等值来自仓库。
- 用 `direct` 模式：pi 默认的 `codemode` 不直接向模型声明工具，和提示词中"调用某工具"的指令对不上。pi 没有 ToolSearch，工具直接声明，所以提示词不提它。
- 斜杠命令由 Runner 展开：pi 只展开以 `/` 开头的消息，而 tag mode 的提示词以 GitHub 上下文开头。展开格式与 pi 自己的一致，`test/pi-sdk/slash-command.test.ts` 用真实的 pi 会话核对；上游的 `.claude/commands/` 要搬到 `.pi/prompts/`。

## 隔离与脱敏

前四项只在设置了 `allowed_non_write_users` 时生效。

| 偏离               | 上游 → 本仓库                                                                                                                                                                                                     | 类别             | 用户可见 |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- | -------- |
| bash 的 env        | Claude Code 内置的黑名单 → 白名单（`src/runner/env-allowlist.ts`），`allowed_bash_env` 放行更多，`subprocess_isolation: false` 关闭（ADR-0002）                                                                   | `pi-capability`  | 是       |
| bash 沙箱          | Claude Code 内置 → bwrap 可用时：新的 PID namespace 和 `/proc`、`no_new_privs`，只有工作目录和空的 `/tmp` 可写；不可用时只过滤 env 并警告（`src/runner/bash-isolation.ts`）                                       | `pi-capability`  | 是       |
| 文件工具与 `/proc` | 无 → 文件工具拒绝访问 `/proc`（`src/runner/tool-permissions.ts`，ADR-0002）                                                                                                                                       | `pi-capability`  | 否       |
| PR 场景的配置恢复  | `SENSITIVE_PATHS` 只有 Claude 的路径 → 补上 `.pi`、`.agents`、`AGENTS.md`、`AGENTS.MD`、`AGENTS.override.md`、`CLAUDE.MD`（`src/github/operations/restore-config.ts`）                                            | `pi-capability`  | 否       |
| 输出脱敏           | 按格式匹配 GitHub、Anthropic、AWS、Slack、JWT → 加上 OpenAI、OpenRouter、Gemini 的格式，以及按值匹配长度不少于 16 的非白名单 env 值（`src/runner/secret-values.ts`、`src/runner/comment-redaction.ts`，ADR-0002） | `multi-provider` | 是       |

| tag mode 的 git 凭据 | 先建分支（`git fetch`、`git ls-remote`），再换成 action 的 token → 先换 token 再建分支；checkout 设了 `persist-credentials: false` 时，私有仓库的分支准备不再因没有凭据失败（`src/modes/tag/index.ts`） | `improvement` | 是 |

- 用白名单而不是黑名单：上游的黑名单在 Claude Code 内部，拿不到；provider 太多，黑名单也列不全。`GH_TOKEN` 同样被去掉，所以 bash 中的 `git push` 和 `gh` 要显式放行它。
- 文件工具在 pi 进程内执行，不经过 bwrap，能直接读 `/proc/self/environ`，所以要单独拦截。检查和执行之间被并行的 bash 换掉符号链接的竞争无法排除。
- 按值脱敏：OpenCode 等 key 格式未知的 provider 只能按值识别；代价是 workflow 自己设置的长 env 值（URL 等）也会被替换。
- pi 的上下文文件接受大写的 `.MD`，在区分大小写的 runner 上是不同的文件，所以要单独列出。

- 跟踪评论的结束标题：Runner 只知道会话正常结束，不知道请求、验收标准或独立 review 是否通过；上游的标题在模型正文写明未完成或检查没跑时仍宣称任务完成。action 不解析正文、勾选框或模型自报的测试结果来判断完成度，完成情况以正文为准。
- 残留的 spinner：单独成行的 `<img>` 在 GitHub 的 Markdown 里开始一个 HTML 块，延续到下一个空行，紧跟其后的清单显示成纯文本。运行出错时模型来不及做最后一次更新，评论就停在这个样子。按 spinner 的图片文件名匹配，评论中的其他图片不动。
- 会话导出：Runner 用内存会话（ADR-0001），pi 的 HTML exporter 不接受内存会话，Execution file 也不是会话 JSONL，所以由 Runner 生成脱敏后的 JSONL 再交给 exporter；原始会话不落盘。exporter 不从包入口导出，按文件导入锁定版本，`test/pi-sdk/session-export.test.ts` 钉住所依赖的行为。按变量名脱敏短值只用于导出：导出包含每个工具结果，而评论和报告按原规则不变。
- 失败运行的未完成工作：长任务在模型或代理故障时失败，改动只在 runner 上，job 结束即丢失。保存只在失败时做，成功的运行由 agent 自己发布，避免把构建产物等杂项推上去。复用分支靠提交 trailer 而不是评论里的链接，分支名按 `branch_name_template` 匹配后再核对 trailer；job 被取消或超时时 `run.ts` 的收尾不执行，不保存。
- 默认运行摘要：完整输出和详细报告默认关闭，长时间运行后在页面上只能看到日志里的 token 和成本合计。摘要只由计数和固定类别拼成，不是脱敏后的事件，所以默认公开也不依赖脱敏；终止类别只说明会话怎样结束，不代表任务完成。
